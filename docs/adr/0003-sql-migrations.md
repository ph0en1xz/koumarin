# ADR 0003 — Schema migrations: hand-written SQL via DbUp

- **Status:** Accepted
- **Date:** 2026-10-08
- **Deciders:** Owner (Mario), Claude
- **Scope:** Who owns the Postgres schema and how it changes. A direct consequence of ADR 0002.

## Context

ADR 0002 makes EF Core read-only. That removes the usual owner of the schema: EF Core migrations
are generated by diffing a write model against a snapshot, and Koumarin will not have a write
model.

Keeping EF migrations anyway would mean maintaining entity classes that nothing writes through,
purely so the tooling can emit DDL. That model has no runtime consumer to keep it honest, so it
drifts from reality silently — and the first symptom is usually a migration that generates the
wrong DDL for a table the application has been writing with Dapper all along.

The schema also contains objects EF Core models poorly or not at all, and they are exactly the
objects that matter here: a partial index (`WHERE published_at IS NULL`), a unique constraint used
deliberately as control flow (ADR 0004), `numeric(19,4)` precision on money, and per-service
Postgres roles with schema-scoped grants.

## Decision

1. **The schema is owned by hand-written SQL migration scripts**, held in the repository and
   applied by **DbUp**. (FluentMigrator is an acceptable substitute; the decision that matters is
   hand-written SQL over generated diffs.)
2. **Forward-only.** No `Down` scripts. A ledger is append-only and a rollback of a schema change
   that has already accepted writes is not a safe operation — recovery is a new forward migration,
   plus a database restore if data is affected.
3. **Scripts are immutable once merged.** DbUp tracks applied scripts in a journal table; editing
   an applied script means it silently never re-runs. Fix forward with a new numbered script.
4. **Naming:** `NNNN__description.sql`, zero-padded and sequential, per schema where helpful
   (`wallet`, `player`, `integration`, `reporting`).
5. **Applied by a dedicated migration runner** — a small console project in the repo, run as a
   Kubernetes Job or init container **before** the new application version rolls out. Services
   never migrate on startup: five replicas racing to apply the same DDL is a failure mode with no
   upside.
6. **Grants are migrations too.** Each service's Postgres role and its schema-scoped privileges are
   created and altered by versioned scripts, so least privilege (ADR 0006) is reproducible rather
   than something configured once by hand.

## Consequences

- **Positive:** the DDL creating the ledger's unique index — the single guarantee the whole money
  path rests on — is written by hand, reviewed, and version-controlled. Nothing infers it.
- **Positive:** partial indexes, check constraints, precise `numeric` types, views for Reporting's
  read models, and role grants are all expressible without fighting a generator.
- **Positive:** one mental model with ADR 0002. Hand-written queries, hand-written schema.
- **Cost accepted:** no auto-generated diffs. Every column and index is typed out, and forgetting
  one is possible in a way it is not with EF migrations. This is the main thing given up.
- **Risk → mitigated:** EF Core read contexts in Reporting can drift from the schema, since neither
  generates the other. Integration tests run the real migrations against a Testcontainers Postgres
  and then query through EF Core (ADR 0007), so drift fails a test rather than a production request.
- **Operational note:** the migration job must be idempotent and safe to re-run, because deploys
  are retried. DbUp's journal provides this; the scripts themselves should still prefer
  `IF NOT EXISTS` where it costs nothing.
- **Forward-only means discipline:** a bad migration cannot be unwound by tooling. Expand/contract
  is the pattern for anything destructive — add the new column, migrate, deploy code, drop the old
  column in a later release.

## Alternatives considered

- **EF Core migrations against a phantom write model.** Keeps familiar tooling and generated
  diffs. Rejected: a model with no runtime consumer drifts, and this one would be responsible for
  the DDL behind the system's only hard money guarantee.
- **Flyway or Liquibase.** Mature, excellent, and the industry default outside .NET. Rejected:
  Flyway's full feature set leans on a JVM, and Liquibase's XML/YAML changelog abstraction adds an
  indirection layer over SQL that ADR 0002 deliberately removed. DbUp is a NuGet package and a
  folder of `.sql` files, which fits a .NET repo with no extra runtime.
- **Grate** (successor to RoundhousE). Close second — good at idempotent/run-always scripts.
  Rejected on familiarity and simplicity grounds, not merit.
- **Raw `psql` scripts applied by hand or by a shell script.** Rejected: no journal, so no reliable
  answer to "has this been applied here?", which is the one thing a migration tool must provide.
- **Migrate on application startup.** Rejected: multiple replicas would race, and a failed
  migration would be discovered as a crash-looping pod rather than a failed job.
